# Definition of Ready – EnAULA

A Definition of Ready (DoR) define os critérios que uma história de usuário precisa cumprir **antes de entrar em uma Sprint**. Uma história só pode ser selecionada para o planejamento quando atende aos critérios necessários para que a equipe consiga compreendê-la, desenvolvê-la e testá-la.

No projeto **EnAULA**, a Definition of Ready considera como base as especificações funcionais, os casos de uso, os requisitos funcionais, as interfaces, a arquitetura e os testes definidos.

## Critérios

### Clareza

- [ ] A história está escrita no formato: **"Como [quem], quero [o quê], para [por quê]"**.
- [ ] O ator da história está identificado.
- [ ] A funcionalidade está relacionada a um **caso de uso ou requisito funcional** .
- [ ] Os critérios de aceitação estão definidos e são verificáveis.
- [ ] O grupo compreende o objetivo da história.
- [ ] O fluxo principal da funcionalidade está definido.
- [ ] Os fluxos alternativos e de exceção estão identificados quando existirem.
- [ ] As pré-condições necessárias para executar a funcionalidade estão conhecidas.
- [ ] As pós-condições esperadas estão definidas.
- [ ] O grupo sabe o que significa **"Done"** para a história.

### Tamanho

- [ ] A história cabe em uma Sprint.
- [ ] Caso a funcionalidade seja grande demais, ela foi dividida em histórias menores.
- [ ] O campo **Size** está preenchido no GitHub Projects: **P, M, G ou GG**.
- [ ] O grupo consegue estimar o esforço necessário para implementar e testar a história.

### Prioridade e contexto

- [ ] O campo **Épico** está preenchido no GitHub Projects.
- [ ] O campo **MoSCoW** está preenchido: **Must, Should, Could ou Won't**.
- [ ] O grupo entende por que a história está sendo incluída na Sprint.
- [ ] O problema ou necessidade que a história resolve está identificado.
- [ ] A história está relacionada a uma funcionalidade prevista para o EnAULA.
- [ ] A prioridade da história está de acordo com os objetivos do projeto.

### Dependências

- [ ] As dependências da história com outras histórias foram identificadas.
- [ ] As histórias das quais esta depende já estão concluídas ou serão entregues antes.
- [ ] As pré-condições necessárias para executar a funcionalidade foram verificadas.
- [ ] As dependências entre os componentes do sistema foram identificadas quando necessário.
- [ ] Dependências com serviços externos foram identificadas quando aplicável.

### Interface

- [ ] A tela relacionada à história está identificada.
- [ ] Existe um wireframe ou protótipo de baixa fidelidade quando a história envolver uma interface.
- [ ] O fluxo de navegação necessário está compreendido.
- [ ] Os dados que o usuário deverá informar ou visualizar estão identificados.
- [ ] As mensagens de sucesso, erro e exceção necessárias estão identificadas.
- [ ] O grupo possui informações suficientes para implementar a interface.

### Testes

- [ ] Os critérios de aceitação estão definidos.
- [ ] Os cenários de sucesso estão identificados.
- [ ] Os principais cenários de erro e exceção estão identificados.
- [ ] As regras de negócio relacionadas à história estão conhecidas.
- [ ] É possível verificar objetivamente se a história foi concluída.
- [ ] Existe uma forma definida de testar a aceitação da história.
- [ ] Quando aplicável, a história está relacionada a um caso de teste de aceitação.

## O que NÃO precisa estar pronto

- [ ] O design final no Figma não precisa estar pronto.
- [ ] Um wireframe ou protótipo de baixa fidelidade é suficiente para orientar a implementação da interface.
- [ ] A solução técnica completamente detalhada não precisa estar pronta.
- [ ] O código da funcionalidade não precisa estar implementado.
- [ ] Os testes não precisam ter sido executados.
- [ ] Todos os diagramas UML não precisam estar concluídos especificamente para a história.
- [ ] A aprovação do professor não é necessária para que a história seja considerada Ready.

## Definition of Ready

Uma história de usuário do **EnAULA** estará **Ready** quando:

- [ ] A história estiver claramente descrita.
- [ ] O ator estiver definido.
- [ ] O objetivo da funcionalidade estiver definido.
- [ ] O caso de uso ou requisito funcional relacionado estiver identificado.
- [ ] Os critérios de aceitação estiverem definidos e forem verificáveis.
- [ ] O fluxo principal estiver compreendido.
- [ ] Os fluxos alternativos e de exceção necessários estiverem identificados.
- [ ] As pré-condições e pós-condições estiverem conhecidas.
- [ ] O tamanho da história estiver estimado.
- [ ] O campo **Size** estiver preenchido.
- [ ] O **Épico** estiver definido.
- [ ] O **MoSCoW** estiver definido.
- [ ] As dependências estiverem identificadas.
- [ ] A interface necessária estiver suficientemente definida.
- [ ] Os cenários de teste estiverem identificados.
- [ ] A equipe compreender o que precisa ser desenvolvido.
- [ ] A equipe concordar que a história está pronta para entrar na Sprint.

## Observação

A **Definition of Ready (DoR)** e a **Definition of Done (DoD)** trabalham juntas.

A DoR garante que a história do **EnAULA** possui informações suficientes para ser iniciada, enquanto a DoD garante que a história atende aos critérios necessários para ser considerada concluída e entregue.
